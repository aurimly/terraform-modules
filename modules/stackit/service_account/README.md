# stackit/service_account

Map-keyed module for STACKIT service accounts in a project.

## Inputs

| Name | Type | Default | Description |
|---|---|---|---|
| `service_accounts` | `map(object)` | — | Map of service accounts keyed by an arbitrary unique ID. |

### `service_accounts` object

| Attribute | Type | Default | Description |
|---|---|---|---|
| `name` | `string` | — | Service account name — only the email's prefix; the API generates the full email from it. Rules (provider-enforced at plan time; the module does not re-validate): starts with a lowercase letter; only lowercase letters, digits, and dashes; no leading/trailing/consecutive dashes; max 20 chars. |
| `project_id` | `string` | — | STACKIT project UUID the service account is created in (provider UUID-validates). |

## Outputs

`service_accounts` — map of service account key => object:

| Attribute | Description |
|---|---|
| `email` | Service account email, generated by the API from the name — `<name>-<random 7–10 chars>@sa.stackit.cloud`. Usable e.g. as the Act-As `subject` in stackit/service_account_role_assignment. |
| `service_account_id` | Service account UUID; usable as that module's `resource_id`. |
| `id` | `{project_id},{email}` — the import ID. |

## Example

```hcl
service_accounts = {
  "ci-bot-prod" = {
    name       = "ci-bot"
    project_id = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  }
  "ci-bot-npd" = {
    name       = "ci-bot"
    project_id = "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy"
  }
}
```

## Notes

- Keys are arbitrary unique identifiers, not names. The same `name` may
  appear in different projects (see the example); only the
  `(project_id, name)` combination must be unique — the module rejects
  duplicates at plan time, the API rejects them at apply ("Name not
  unique").
- Both `name` and `project_id` are create-only (the provider sets
  `RequiresReplace()` on both, and the upstream update always errors):
  renaming a service account or moving it to another project replaces it —
  the identity is briefly absent between destroy and create, the email
  changes (new random suffix), and the `service_account_id` (UUID) changes
  too, so grants referencing it (the
  `stackit/service_account_role_assignment` module's `resource_id`) must be
  re-pointed and are replaced themselves. Renaming a map key has the same
  effect (the resource address changes).
- The email cannot be chosen independently: the name is only the prefix,
  the API generates the full email
  (`<name>-<random 7–10 chars>@sa.stackit.cloud`).
- Creation takes a few seconds (the provider waits ~5s for the IAM cache
  to settle after create) — latency only, no consumer action.
- No upstream deletion protection: `destroy` deletes the service accounts
  immediately and issued keys stop working. Use Terragrunt- or
  pipeline-level safeguards if that is unwanted. If a service account is
  deleted out of band, the provider drops it from state and the next apply
  recreates it — with a new random email suffix.
- No provider experiment flag is needed — unlike
  `stackit/service_account_role_assignment` (`experiments = ["iam"]`), the
  service account resource is stable and non-experimental.
- Chaining: pass `service_accounts["<key>"].service_account_id` to
  `stackit/service_account_role_assignment`'s `resource_id` and the
  `email` as a `subject` when granting Act-As on other service accounts
  (Terragrunt `dependency`).
- The runner needs rights to manage service accounts in the target project
  (e.g. a project owner/admin role — guidance, not a documented
  permission). Provider authentication (service account key flow) is
  configured at the consumer's root level.
- The provider floor `>= 0.113.0` matches the
  `stackit/service_account_role_assignment` module so both behave
  identically when consumed together; the resource itself predates that
  version and the current shape (including `service_account_id`) is
  confirmed against it.

## Import

`stackit_service_account` ← `{project_id},{email}`

Use the `import {}` block with `id = "${project_id},${email}"`. Both
required attributes must be set in config. The provider parses the name
from the email by stripping the random suffix (`foo` from
`foo-aBc2defg@sa.stackit.cloud`), so the import plans clean only when the
config `name` equals that prefix — using the full local part would show a
spurious replacement diff.
